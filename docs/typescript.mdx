`@kensa/sdk` provides TypeScript authoring helpers and a Vitest adapter. It imports `@kensa/core` directly, so local TypeScript evals do not start a Python process, child engine, or local service.

## Install

```bash
pnpm add -D @kensa/sdk vitest
```

## Write a Vitest eval

`kensaTest(...)` registers a normal Vitest test. `observe` calls your agent and returns its output and trace evidence. `check` turns that observation into a typed check result.

```typescript title="refund.eval.test.ts"
import { kensaTest } from "@kensa/sdk/vitest";

const emptyTrace = {
  spans: [],
  agent_runs: [],
  tools: [],
  tool_calls: [],
  incomplete: false,
  incomplete_reason: null,
  duration_ms: 0,
  cost_usd: null,
  known_cost_usd: null,
  cost_available: false,
  llm_turns: 0,
};

kensaTest("does not issue an unsupported refund", {
  case: {
    id: "refund_without_order_history",
    input: "Refund my last charge. I do not have an order ID.",
    metadata: {},
  },
  observe: async (evaluationCase) => ({
    output: await refundAgent(evaluationCase.input),
    output_recorded: true,
    trace: emptyTrace,
    failure: null,
  }),
  check: ({ observation }) => {
    const passed = observation.output === "I need order history first.";
    return {
      id: "refund_policy",
      outcome: passed ? "satisfied" : "unsatisfied",
      failure: passed
        ? null
        : {
            category: "agent",
            kind: "assertion",
            message: "The agent offered an unsupported refund.",
            evidence: { output: observation.output },
          },
    };
  },
});
```

Run it with your existing Vitest command:

```bash
pnpm vitest run
```

The default expected verdict is `pass`. Pass `{ expectedVerdict: "fail" }` as the third argument when a non-passing result is the behavior under test. Use `verify(result)` in that options object for additional assertions on the completed evaluation.

## Run without Vitest

Use `defineCase(...)` and `runEvaluation(...)` from `@kensa/sdk` when another TypeScript test runner or application owns execution:

```typescript
import { defineCase, runEvaluation } from "@kensa/sdk";

const evaluationCase = defineCase({
  id: "greeting",
  input: "Hello",
  metadata: {},
});

const result = await runEvaluation({
  case: evaluationCase,
  observe: runAgent,
  check: checkGreeting,
});
```

Both callbacks may be synchronous or asynchronous. Callback exceptions propagate to the caller. Invalid cases, observations, and check results fail closed through the core contract.

## Release identity

Every release includes the same `kensa.build_manifest.v1` document in `@kensa/core`, `@kensa/sdk`, the Python wheel, and the release assets. The npm packages export it as `@kensa/core/build-manifest.json` and `@kensa/sdk/build-manifest.json`.

Pin the SDK release and record both `digest` and `contract_digest` when another system consumes Kensa artifacts. The manifest identifies the exact core, engine, Python SDK, TypeScript SDK, contracts, schemas, and conformance fixtures in that release. Do not coordinate those identities as a loose list of package versions.

See [Artifact and release migration](/migration) before consuming artifacts produced by another Kensa version.
